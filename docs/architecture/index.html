1. Overview

Signal adalah aplikasi web untuk belajar dan bermain sandi Morse.

  • Pengguna: orang yang ingin mempelajari atau berlatih sandi Morse, terutama pemula.
  • Tujuan utama: memperkenalkan sandi Morse melalui game yang langsung dapat dimainkan, lalu mengajak pengguna belajar secara terstruktur di area private.
  • Area publik: landing page yang berisi Morse Explorer, Tantangan Morse, Kirim Pesan Morse, dan Morse Translator, yang dapat digunakan tanpa akun.
  • Area private (area belajar): Lesson, Practice, Listening, Quiz, dan Progress. Progress tersimpan per akun dan dapat diakses dari perangkat mana pun.

2. Siklus Pengembangan (SDLC)

Dokumen ini disusun mengikuti tahap-tahap Software Development Life Cycle (SDLC): mulai dari perencanaan, analisis kebutuhan, desain, implementasi, testing, deployment, hingga maintenance. Setiap tahap menghasilkan deliverable yang menjadi dasar tahap berikutnya, sehingga tim dapat menelusuri alasan di balik setiap keputusan teknis.

Model yang Digunakan

Signal dikembangkan dengan model iteratif per milestone. Perencanaan, analisis kebutuhan, dan desain dikerjakan di awal untuk seluruh versi awal (hasilnya dituangkan dalam dokumen ini). Setelah itu, pekerjaan dibagi menjadi beberapa milestone. Setiap milestone melewati siklus yang sama:

  1. Implementasi fitur yang termasuk dalam milestone tersebut.
  2. Testing: unit test dan end-to-end test untuk fitur baru, ditambah pengujian ulang fitur dari milestone sebelumnya.
  3. Deployment ke staging agar hasilnya dapat dicoba dan ditinjau sebelum milestone berikutnya dimulai.

Temuan dari staging dapat mengubah desain atau menjawab pertanyaan di Hal yang Perlu Dikonfirmasi. Perubahan tersebut dicatat kembali di dokumen ini. Deployment ke production baru dilakukan di milestone terakhir.

3. Perencanaan

Tujuan Proyek

Signal dibuat untuk membantu orang, terutama pemula, mengenal dan menguasai sandi Morse. Tujuan versi awal:

  • Memperkenalkan Morse tanpa hambatan. Pengunjung dapat langsung bermain game, menggunakan Morse Translator, dan mencoba Morse Explorer dari landing page tanpa membuat akun.
  • Menyediakan jalur belajar terstruktur. Pengguna yang login dapat mengikuti Lesson, berlatih encode dan decode di Practice, melatih pendengaran di Listening, mengerjakan Quiz, dan memantau Progress.
  • Mendorong belajar bersama. Game dapat dibagikan melalui link dan dimainkan bersama teman, lengkap dengan score per pemain.
  • Menjaga penilaian tetap adil. Score Quiz, Tantangan Morse, dan tebakan pesan dihitung di server.
  • Menghadirkan identitas visual yang membantu belajar. Gaya Radio Communication digunakan di seluruh UI, dengan waveform dan LED yang menunjukkan timing Morse yang sebenarnya.

Ruang Lingkup Versi Awal

Termasuk
  • Landing page dengan dua kartu game, form bergabung, dan ajakan belajar.
  • Game room di /g/$gameId: link unik, popup nickname, tombol "Salin link".
  • Tantangan Morse dengan soal yang sama untuk semua pemain, batas waktu, dan leaderboard.
  • Kirim Pesan Morse dengan feed bersama, maksimal 3 tebakan per pesan, dan papan score.
  • Morse Translator dua arah dengan waveform dan bunyi.
  • Morse Explorer untuk huruf A–Z dengan lima jenis representasi.
  • Lima jenis representasi sebagai tampilan soal dan koreksi di Practice, Listening, Tantangan Morse, dan Kirim Pesan Morse melalui MorseViewer mode question.
  • Authentication email + password (daftar, login, logout).
  • Lesson, Practice, Listening, Quiz, dan Progress di area private.
  • Gaya Radio Communication dan color palette Signal di semua halaman, termasuk mode gelap.
  • Konten Lesson dan Quiz yang diisi melalui seed.
Belum termasuk
  • Real-time update (WebSocket). Leaderboard dan feed pesan menggunakan polling 5 detik.
  • Background job. Game lama dibersihkan dengan script manual.
  • Verifikasi email, reset password, dan login sosial.
  • Pesan pribadi ke satu pemain tertentu.
  • Moderasi nickname dan isi pesan (filter kata, tombol "Laporkan").
  • Rate limit pembuatan game.
  • Angka 0–9 dan tanda baca di grid Morse Explorer.
  • Menyimpan hasil atau riwayat Practice dan Listening.
  • Hasil game di Progress, dan penggunaan nama akun di game.
  • Pengaturan pengguna yang tersimpan di server (pengaturan Listening hanya di localStorage).
  • Halaman admin untuk mengelola konten.

Milestone

Urutan milestone mengikuti ketergantungan antar bagian. lib/morse.ts dan component radio dibutuhkan semua fitur, sehingga dikerjakan paling awal. MorseViewer dan lib/morse-audio.ts dibuat bersama Explorer dan Translator, lalu digunakan kembali oleh game, Lesson, Practice, dan Listening. Karena itu, mode question dan dukungan teks multi-karakter di MorseViewer sudah dibuat di M2. lib/prompts.ts dibuat bersama Tantangan Morse, lalu digunakan kembali oleh Practice dan Listening. Progress dikerjakan terakhir karena membaca data Lesson dan Quiz.

Batasan

  • Stack telah ditetapkan: TanStack Start, TypeScript, TanStack Router, PostgreSQL, dan Drizzle ORM. TanStack Query hanya digunakan untuk polling di game. Better Auth adalah satu-satunya dependency utama di luar stack tersebut.
  • Tidak ada real-time update di versi awal. Pembaruan leaderboard dan feed pesan menggunakan polling.
  • Tidak ada background job di versi awal. Pembersihan game lama dijalankan dengan script manual.
  • Dua area dengan identitas berbeda: game publik menggunakan nickname dan cookie per game, sedangkan area private menggunakan akun email + password. Kedua area tidak saling berelasi di database.
  • Palette dan visual style telah ditetapkan: Navy, Blue, Cyan, Off-white, aturan Cyan = dot dan Blue = dash, serta gaya Radio Communication di semua UI.
  • Tidak ada layanan email, sehingga verifikasi email dan reset password belum tersedia.

Asumsi

  • Target pengguna adalah pemula yang menggunakan browser modern, baik di desktop maupun ponsel.
  • Konten Lesson dan Quiz disiapkan oleh developer dan diisi melalui seed. Belum ada halaman admin.
  • Volume pengguna awal relatif kecil sehingga polling 5 detik dan query agregat Progress tidak membebani server.
  • Game bersifat sementara. Pemain yang berganti perangkat dianggap pemain baru.
  • Selama belum ada keputusan, rekomendasi sementara di Hal yang Perlu Dikonfirmasi digunakan sebagai acuan, misalnya 10 soal dan 90 detik untuk Tantangan Morse serta 5–20 WPM dengan nada 600 Hz untuk Listening.

Architecture

  • components/radio/RadioShell.tsx dipasang di routes/__root.tsx, sehingga semua halaman secara otomatis menggunakan header, navigasi channel, dan status bar yang sama.
  • components/radio/ berisi component visual yang digunakan bersama: RadioShell, RadioPanel, MorseSymbols, SignalLed, SignalMeter, ChannelDisplay, dan Waveform.
  • lib/morse.ts mendapat fungsi baru toTimings(code) untuk mengubah kode menjadi urutan on/off dalam satuan unit (titik 1, strip 3, jeda simbol 1, jeda huruf 3, jeda kata 7).
  • Waveform menggambar SVG dari toTimings. Web Audio API pada listening exercise akan menggunakan fungsi yang sama, sehingga gambar dan bunyi selalu sinkron.
  • Tidak menggunakan library tambahan. Semua elemen dibuat dengan SVG, Tailwind, dan animasi CSS.
  • Font monospace menggunakan stack sistem (ui-monospace) untuk label, angka, channel, dan layar radio. Teks panjang seperti penjelasan lesson tetap menggunakan font sans-serif agar mudah dibaca.
  • Component shadcn/ui (Button, Dialog, Input, Card) diberi variant radio melalui token palette dan class Tailwind, bukan dibuat ulang.

Aturan Penggunaan

  • Elemen radio harus membantu memahami Morse, bukan hanya hiasan. Waveform dan LED menunjukkan timing yang sebenarnya.
  • Simbol titik/strip selalu disertai teks alternatif untuk screen reader, misalnya aria-label="titik titik titik".
  • Animasi (LED berkedip, playhead, glow) dimatikan jika pengguna memilih prefers-reduced-motion.
  • Efek glow tidak boleh menurunkan kontras teks. Teks utama tetap Off-white di atas Navy.
  • Label frekuensi bersifat dekoratif dan diberi aria-hidden="true". Navigasi channel tetap memiliki nama yang jelas, misalnya CH-01 LEARN dengan label "Lesson".
  • Teks yang harus dibaca lama (materi lesson, pesan error) tidak ditulis seluruhnya dalam huruf kapital monospace.

Pros dan Cons

Kelebihan
  • Memberikan identitas visual yang kuat dan sesuai dengan tema Morse.
  • Waveform membantu pemula memahami perbedaan panjang titik, strip, dan jeda.
  • Satu gaya untuk seluruh aplikasi membuat landing page, game, dan area private terasa sebagai satu produk.
  • Component digunakan ulang di semua halaman, sehingga konsistensi gaya mudah dijaga.
  • Selaras dengan palette Navy dan Cyan.
Kekurangan
  • Terlalu banyak elemen dapat membingungkan pemula, terutama di Lesson dan Quiz. Oleh karena itu, elemen di kedua halaman tersebut dibatasi hanya pada elemen yang membantu proses belajar.
  • Pembuatan component visual membutuhkan waktu tambahan, begitu juga penyesuaian semua component shadcn/ui.
  • Animasi dan glow perlu diuji agar tetap ringan di perangkat mobile.
  • Panel gelap di mode terang perlu diatur agar tidak terlalu kontras dengan halaman.

Spesifikasi ID Game

  • Format: 12 karakter base62, misalnya /g/k7Qm2xPa9TbZ. Panjang ini memberi sekitar 71 bit acak sehingga praktis tidak dapat ditebak.

Konvensi Kode

  • TypeScript strict. Opsi strict aktif. Hindari any; jika tipe data belum pasti, gunakan unknown, kemudian lakukan validasi.
  • Folder berbasis fitur. Kode fitur berada di features/<nama-fitur>/ (server.ts, components/, dan file logic seperti grade.ts). Component yang digunakan oleh lebih dari satu fitur berada di components/, dan logic yang tidak bergantung pada UI atau database berada di lib/, sesuai Struktur Project.
  • Urutan di setiap Server Function selalu sama: validasi input dengan Zod, pemeriksaan identitas dengan requireUser() atau requirePlayer(gameId), kemudian eksekusi logic dan akses ke database. userId dan playerId tidak pernah diterima dari input client.
  • Tidak ada business logic di component. Component hanya menampilkan data dan menangani interaksi. Penilaian, perhitungan score, dan aturan game berada di Server Function atau di fungsi murni seperti features/quiz/grade.ts agar mudah diuji.
  • Logic Morse hanya di lib/morse.ts. Tabel kode, encode, decode, normalize, dan toTimings tidak boleh diduplikasi di fitur lain. Jika sebuah fitur membutuhkan fungsi Morse baru, fungsi itu ditambahkan ke lib/morse.ts beserta unit test-nya.
  • Warna hanya dari design token. Gunakan token di styles/app.css (misalnya signal-navy, morse-dot, primary), bukan nilai hex langsung di component. Pengecualian sementara hanya green-600 dan red-600 untuk feedback benar dan salah.
  • Penamaan:
    • File component dan nama component menggunakan PascalCase, misalnya NicknameDialog.tsx.
    • Fungsi dan Server Function menggunakan camelCase yang diawali kata kerja, misalnya createGame, getLeaderboard, dan submitQuiz.
    • File di lib/ menggunakan kebab-case, misalnya morse-audio.ts.
    • Nama tabel dan kolom database menggunakan snake_case, dengan nama tabel jamak, misalnya game_players dan last_played_at.
    • Nama file route mengikuti konvensi TanStack Router, misalnya $gameId.tsx dan _authed.tsx.

Kriteria Penerimaan

Sebuah milestone diterima jika semua syarat berikut terpenuhi:

  • Semua use case milik milestone tersebut (misalnya GR1–GR5, CH1–CH5, dan MS1–MS5 untuk M3) berjalan sesuai user flow di bab fitur.
  • Skenario utama yang terkait lulus, dan tidak ada test yang gagal di CI.
  • Tidak ada bug berprioritas kritis atau tinggi yang masih terbuka.
  • Telah diperiksa di Chrome, Firefox, dan Safari versi terbaru, serta di setidaknya satu ponsel (iOS atau Android).

Data Testing

  • Database terpisah. Integration test menggunakan database PostgreSQL khusus test melalui TEST_DATABASE_URL, tidak pernah menggunakan database local, staging, atau production. Di CI, database ini dijalankan sebagai service container.
  • Schema dan seed. Sebelum test berjalan, semua migration dijalankan lalu db/seed.ts mengisi lesson dan quiz, sehingga data test sama dengan data aplikasi.
  • Reset antartest. Data yang dibuat test (pengguna, game, attempt) dihapus setelah setiap test, misalnya dengan menjalankan test di dalam transaksi yang di-rollback atau dengan truncate tabel non-konten. Setiap test dapat berjalan sendiri tanpa bergantung pada urutan.
  • End-to-end test di staging menggunakan akun dan game yang dibuat khusus oleh test, dengan nama yang mudah dikenali, misalnya diawali e2e-, agar mudah dibersihkan.

Migrasi Database saat Deploy

  • Migration dijalankan sebelum versi baru aktif. Dengan demikian, kode baru tidak pernah berjalan di atas schema lama.
  • Migration harus backward compatible. Versi lama aplikasi masih berjalan selama beberapa saat setelah migration, dan mungkin perlu digunakan kembali saat rollback. Contohnya, kolom baru ditambahkan sebagai nullable atau dengan nilai default. Kolom yang tidak lagi digunakan baru dihapus pada rilis berikutnya, setelah tidak ada kode yang membacanya.
  • Backup sebelum migration production. Buat backup atau snapshot manual sebelum migration dijalankan, terutama untuk migration yang mengubah atau menghapus data.
  • Seed dijalankan setelah migration jika ada perubahan konten lesson atau quiz. Seed aman dijalankan ulang karena menggunakan upsert berdasarkan slug.

Rollback

  • Aplikasi: deploy ulang versi sebelumnya yang masih tersimpan di host. Karena migration bersifat backward compatible, versi lama tetap dapat berjalan di atas schema baru.
  • Database: perubahan diperbaiki dengan migration baru (roll forward), bukan dengan mengubah atau menghapus migration lama.
  • Data rusak: jika migration merusak data, restore dari backup yang dibuat sebelum migration. Langkah ini menjadi pilihan terakhir karena data yang masuk setelah backup akan hilang.

24. Maintenance

Setelah rilis, maintenance menjaga aplikasi tetap berjalan, data tetap aman, dan perubahan tetap teratur. Prosesnya dibuat sederhana dan memanfaatkan fitur bawaan provider sebanyak mungkin.

Monitoring dan Logging

  • Error logging di server. Setiap error di Server Function dicatat beserta konteks request: nama Server Function, route, waktu, dan ID pengguna atau pemain jika ada. Log ditulis ke output standar agar terbaca di dashboard host.
  • Data yang tidak boleh dicatat: password, token session, token pemain, isi cookie, kunci jawaban quiz dan Tantangan Morse, serta teks pesan yang belum terbuka. Input Server Function tidak di-log secara utuh.
  • Uptime check. Layanan uptime monitor gratis memeriksa landing page setiap beberapa menit dan mengirim notifikasi jika aplikasi tidak dapat diakses.
  • Metrik dasar dihitung langsung dari tabel yang telah tersedia, tanpa layanan analytics tambahan:
    • Game yang dibuat: jumlah baris games per hari, dari created_at.
    • Pemain aktif: jumlah baris game_players baru dan game dengan last_played_at terbaru.
    • Pendaftaran: jumlah baris user baru, dari created_at.
    • Quiz attempt: jumlah baris quiz_attempts per hari, dari created_at.

Backup Database

  • Backup otomatis harian dari provider PostgreSQL managed untuk database production. Pastikan paket yang dipilih menyediakan fitur ini.
  • Retention berkisar antara 7 hingga 30 hari. Rekomendasi sementara adalah 14 hari, yang memadai untuk menemukan masalah data yang baru disadari beberapa hari kemudian.
  • Backup manual dibuat sebelum setiap migration production dan sebelum menjalankan script pembersihan data.
  • Restore test dilakukan secara berkala, misalnya setiap tiga bulan: restore backup ke database sementara, lalu periksa apakah aplikasi dapat berjalan dengan data tersebut. Backup yang belum pernah diuji belum tentu dapat digunakan.

Pembersihan Data

Versi awal tidak memiliki background job, sehingga game yang telah lama tidak aktif dibersihkan dengan script manual berdasarkan kolom last_played_at.

  • Lokasi: script disimpan di db/, misalnya db/cleanup-games.ts, dan dijalankan dari komputer developer dengan DATABASE_URL production.
  • Aturan: hapus baris games dengan last_played_at lebih lama dari batas yang ditentukan. Rekomendasi sementara adalah 30 hari, sama dengan masa berlaku cookie pemain, karena setelah itu pemain tidak lagi dikenali di game tersebut. Data turunan (game_players, challenge_rounds, challenge_results, messages, message_guesses) ikut terhapus melalui foreign key cascade.
  • Jadwal: dijalankan sebulan sekali, atau lebih cepat jika ukuran database mendekati batas paket provider.
  • Cara aman: buat backup terlebih dahulu, jalankan script dalam mode dry run untuk melihat jumlah game yang akan dihapus, lalu jalankan penghapusan yang sebenarnya.
  • Data area private (akun, progress, attempt) tidak termasuk dalam pembersihan ini.

Pembaruan Dependency

  • Pemeriksaan bulanan untuk dependency yang memiliki versi baru, terutama TanStack Start, Better Auth, Drizzle, dan Zod.
  • Security patch dipasang sesegera mungkin setelah ada peringatan keamanan, misalnya dari fitur security alert di GitHub.
  • Setiap pembaruan dikerjakan di branch terpisah (chore/update-dependencies) dan harus lulus semua test di CI serta diperiksa di staging sebelum masuk production.
  • Pembaruan versi major dikerjakan satu per satu, dengan membaca catatan perubahan library tersebut terlebih dahulu.

25. Ringkasan Pros dan Cons

Kelebihan
  • Mudah dicoba: pengunjung dapat langsung bermain atau menggunakan Translator dari landing page tanpa akun.
  • Sosial: game dapat dibagikan melalui link dan dimainkan bersama, lengkap dengan leaderboard.
  • Progress belajar aman: progress disimpan per akun sehingga dapat dibuka di perangkat mana pun.
  • Score tidak dapat dicurangi: jawaban Quiz, Tantangan, dan tebakan pesan dinilai di server.
  • Satu aplikasi: kedua area menggunakan TanStack Start, database, dan lib/morse.ts yang sama.
  • Tampilan konsisten: seluruh UI menggunakan gaya Radio Communication dan palette Navy, Blue, Cyan, Off-white melalui component dan token yang sama.
  • Lima representasi di semua latihan dan game: satu MorseViewer digunakan untuk belajar, soal, dan koreksi, sehingga pengguna berlatih mengenali Morse dalam bunyi, cahaya, timeline, chart, dan simbol.
Kekurangan
  • Dua sistem identitas: game menggunakan cookie pemain, sedangkan area private menggunakan session.
  • Tidak real-time: leaderboard dan pesan diperbarui melalui polling setiap 5 detik.
  • Hasil game tidak terhubung ke akun dan tidak muncul di Progress.
  • Belum ada moderasi untuk nickname dan isi pesan di area publik.
  • Area publik rentan spam hingga rate limit ditambahkan.
  • Audio bergantung pada browser: Web Audio API diblokir sebelum interaksi dan mungkin tidak berbunyi dalam mode senyap.
  • Konten dikelola melalui seed dan belum tersedia halaman admin.
  • MorseViewer menjadi lebih kompleks: mode question, teks multi-karakter, dan penggunaan di tujuh fitur membuat setiap perubahan perlu diuji di banyak halaman.
